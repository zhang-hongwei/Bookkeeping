# Feature Specification: 净资产闭环 + 首份 AI 报告 (Phase 1)

**Feature Branch**: `002-net-worth-ai-report`
**Created**: 2026-06-29
**Status**: Draft
**Input**: User description: "继续完成 docs/product-design/ai-wealth-manager.md 指定全部的规格"（本 spec 对应《AI 财富管家产品设计》中的 **Phase 1 ⭐ 价值验证版**，依赖 Phase 0 复式记账地基）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一眼看清我的净资产与变化趋势 (Priority: P1)

作为一个想知道「我到底变富了没有」的人，我希望打开应用就能看到当前总资产、总负债、净资产，以及一条随时间变化的净资产曲线，而不是一堆零散的流水。

**Why this priority**: 这是产品的北极星——净资产曲线。Phase 0 让账目变准了，但用户还看不到「净资产」这个终极产出。把净资产仪表盘 + 曲线做出来，才算真正回答了「我变富了吗」，是验证整个产品假设的核心。

**Independent Test**: 用户录入若干笔真实收支/转账后，仪表盘的「总资产 / 总负债 / 净资产」与手动盘点一致，净资产曲线随每日快照连续呈现且数值自洽。即便只交付这一个故事，用户也得到了一个能回答「我变富了吗」的最小闭环。

**Acceptance Scenarios**:

1. **Given** 用户已有若干账户（现金、储蓄、信用）与历史交易，**When** 打开净资产仪表盘，**Then** 看到总资产、总负债、净资产三个核心数字，且净资产 = 总资产 − 总负债，与逐账户汇总一致。
2. **Given** 用户连续多天有交易，**When** 查看净资产曲线，**Then** 曲线按日连续呈现净资产变化，任意一天的净资产值与当天账户余额汇总一致。
3. **Given** 用户进行了一笔转账（如现金 ¥500 → 储蓄），**When** 刷新仪表盘，**Then** 净资产总额不变（仅资金位置变化），曲线不因此产生虚假的「变富/变穷」波动。
4. **Given** 用户查看「今日变化」，**When** 当天有收支发生，**Then** 显示相对昨日净资产的变动额与方向。

### User Story 2 - 拍照即可记账（账单/支付截图） (Priority: P2)

作为一个嫌手动录入麻烦的人，我希望能拍一张账单或支付截图，系统自动识别出交易并让我确认，而不必逐笔敲键盘。

**Why this priority**: 录入摩擦是头号死亡线。Phase 0 已有批量 CSV 导入，但「随手拍一张」比导出文件更贴合日常场景，是降低摩擦、提升留存的高杠杆能力。

**Independent Test**: 拍一张支付宝/微信支付截图，系统识别为候选交易（金额/时间/对方/建议分类），用户确认后正确落库且账目平衡。

**Acceptance Scenarios**:

1. **Given** 用户拍了一张支付截图，**When** 上传识别，**Then** 系统返回候选交易（金额、时间、对方/备注、建议分类、建议账户）并进入可确认状态。
2. **Given** 识别出的候选交易，**When** 用户确认，**Then** 交易落库、相关账户余额正确更新、账目保持平衡，且该笔记录来源标记为「截图识别」。
3. **Given** 截图模糊或多笔交易难以可靠区分，**When** 识别置信度低，**Then** 系统明确标注低置信度并要求人工确认/补全，绝不静默错误落库。

### User Story 3 - 每月一份看得懂、能信的财务报告 (Priority: P3)

作为一个不懂财务的人，我希望每月收到一份财务报告，告诉我这个月赚了多少、花了多少、存了多少、财务健不健康，而且报告里的每一个数字我都能信、不是 AI 编的。

**Why this priority**: 这是产品差异化的核心——「规则引擎负责准确，LLM 负责表达」。首份月报跑通「真相源数据 → 规则结论 → LLM 表达」流水线，验证「0 幻觉 AI 报告」的核心承诺，是 Phase 1 的价值验证关键。

**Independent Test**: 生成一个月度报告，报告中所有具体数字结论（储蓄率、负债率、应急金月数、收支总额）均由规则引擎计算、可逐项追溯到账目数据，LLM 只负责自然语言解释；月报打开即用。

**Acceptance Scenarios**:

1. **Given** 用户本月有完整收支数据，**When** 触发生成月度报告，**Then** 报告包含本月收入/支出/结余总额、储蓄率、负债率、应急金月数，所有数字均来自规则引擎计算。
2. **Given** 报告中的数字结论，**When** 用户查看任意结论（如「储蓄率 23%」），**Then** 该结论可追溯到对应的账目数据与规则，不存在 LLM 自行推算的数字。
3. **Given** LLM 生成的解读文字，**When** LLM 服务异常或超时，**Then** 报告降级为规则结论的模板文本，数字结论仍正确呈现，不因 LLM 失败而丢失关键信息。
4. **Given** 报告生成后数据发生变化，**When** 用户查看已生成报告，**Then** 系统提示「数据已变化，报告基于生成时数据」并可重新生成。

### User Story 4 - 一个直观的财务健康分 (Priority: P4)

作为一个想知道自己财务状况好不好的人，我希望看到一个 0–100 的财务健康分和雷达图，一眼知道哪方面强、哪方面弱。

**Why this priority**: 健康分把多维财务状况压缩为一个可比、可追踪的指标，是仪表盘之上的「总结层」。它复用规则引擎结论，是月报之外的日常抓手。

**Independent Test**: 给定一组账目数据，健康分按既定维度（储蓄率/负债率/应急金/投资率/现金流稳定性）加权计算，输出总分 + 各维度雷达图，且与规则结论一致。

**Acceptance Scenarios**:

1. **Given** 用户有足够数据，**When** 查看财务健康分，**Then** 显示 0–100 总分及各维度（储蓄率/负债率/应急金/投资率/现金流）的雷达图。
2. **Given** 某维度数据不足（如新用户无历史现金流），**When** 计算健康分，**Then** 缺失维度被合理标注/降权，不编造数字。

---

### Edge Cases

- **净资产曲线历史回填**：用户首次启用净资产功能时，应基于已有历史交易回算历史每日快照，而非从启用当天才开始有曲线。
- **实物资产/房产**：Phase 1 不含实物资产估值（属 Phase 2），净资产仅含现金/存款/信用类，避免低流动性资产污染曲线（对应设计 P6「诚实估值」）。
- **负净资产（资不抵债）**：负债 > 资产时净资产为负，曲线需如实呈现，不做掩盖。
- **截图识别多笔**：一张截图含多笔交易时，需逐笔拆分候选交易并各自确认；无法可靠拆分时标注低置信度交人工处理。
- **报告期数据不完整**：当月数据不足（如月中生成）时，报告需标注「数据不完整」并说明影响，不静默给出看似完整的结论。
- **多币种**：Phase 1 仍为单币种 CNY；跨币种不在本阶段。
- **快照与实时聚合一致性**：当历史交易被编辑/删除时，受影响日期的快照需重算，曲线不可残留旧值。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在 Phase 0 账户与交易基础上，提供净资产仪表盘：展示总资产、总负债、净资产，且净资产 = 总资产 − 总负债。
- **FR-002**: 系统 MUST 维护每日净资产快照（总资产/总负债/净资产/按类型分项），净资产曲线读取快照而非实时聚合全量历史流水。
- **FR-003**: 系统 MUST 在交易发生、编辑、删除后，更新相关日期的净资产快照，保证曲线与账目始终一致。
- **FR-004**: 系统 MUST 对转账类操作保证净资产不变（沿用 Phase 0 不变式），曲线不产生虚假波动。
- **FR-005**: 系统 MUST 支持截图记账：识别账单/支付截图为候选交易（金额/时间/对方/建议分类/建议账户），经用户确认后落库，并标记来源为「截图识别」。
- **FR-006**: 系统 MUST 对截图识别结果标注置信度；低置信度时必须要求人工确认或补全，不得静默错误落库。
- **FR-007**: 系统 MUST 提供规则引擎，确定性地计算月度财务结论：收入/支出/结余总额、储蓄率、负债率、应急金月数。
- **FR-008**: 系统 MUST 提供月度财务报告：规则结论作为事实输入，LLM 仅负责自然语言表达与个性化解读；报告中所有具体金额/比率结论必须来自规则引擎，禁止 LLM 自行推算。
- **FR-009**: 系统 MUST 在 LLM 失败时，将报告降级为规则结论的模板文本，保证关键数字结论不丢失。
- **FR-010**: 系统 MUST 检测报告生成后数据是否变化，提示用户并提供重新生成能力。
- **FR-011**: 系统 MUST 提供 0–100 财务健康分，按储蓄率/负债率/应急金/投资率/现金流稳定性等维度加权计算，并给出各维度雷达图。
- **FR-012**: 系统 MUST 在某维度数据不足时对健康分做合理降权/标注，不得编造缺失数值。
- **FR-013**: 系统 MUST 保证所有数据按用户隔离；报告、快照、健康分均仅限本人。

### Key Entities *(include if feature involves data)*

- **净资产快照 (Net Worth Snapshot)**：某一日的净资产物化记录，含日期、总资产、总负债、净资产、按资产类型的分项明细。曲线读取此表，避免实时聚合历史全量流水。
- **资产/负债 (Asset / Liability)**（本阶段轻量版）：现金/存款类资产（=账户余额聚合）、信用类负债；完整的实物资产与负债明细属 Phase 2。
- **规则结论 (Rule Finding)**：规则引擎产出的结构化确定性结论，含指标、数值、判定（verdict）、风险等级；可测试、可审计、零幻觉，作为 LLM 表达层的事实输入。
- **AI 财务报告 (AI Report)**：月度报告产物，正文落文档/Block 层，元数据记录报告期、类型、评分、生成时间、数据指纹（用于检测数据变化后失效）。
- **财务健康分 (Financial Health Score)**：基于多维度规则结论加权得到的 0–100 综合分，含各维度分项与雷达图。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：连续 30 天真实使用后，净资产曲线任意一天的值与当天逐账户手动盘点一致，曲线与账目不一致发生率 = 0。
- **SC-002**：任意转账操作后，净资产总额不变（仅改变资金位置），曲线无虚假波动。
- **SC-003**：月度报告中所有具体金额/比率结论 100% 来自规则引擎，LLM 自行推算数字的幻觉发生率 = 0（可逐项追溯）。
- **SC-004**：LLM 服务异常时，报告仍能呈现全部规则结论数字（降级模板文本），关键结论丢失率 = 0。
- **SC-005**：标准支付截图识别为候选交易的核心字段（金额/时间）准确率 ≥ 90%；低置信度识别被拦截要求人工确认。
- **SC-006**：财务健康分在账目数据不变时稳定可复现（确定性计算）。
- **SC-007**：净资产仪表盘首屏加载即在用户可接受的等待内呈现总资产/总负债/净资产三项核心数字（读取快照而非全量聚合）。

## Assumptions

- 本阶段依赖 Phase 0 已交付的复式记账地基（账户、交易、分录、平衡不变式、分类、账单导入）。
- 净资产在本阶段仅含现金/存款类资产与信用类负债；房产/车辆等实物资产估值、房贷/车贷等完整负债明细属 Phase 2，本阶段不污染主曲线（对应设计 P6「诚实估值」与 D2 默认）。
- 单币种 CNY；多币种、汇率换算不在本阶段。
- 截图识别与报告 LLM 表达层依赖现有 AI 对话/Pipeline 能力（在线）。
- 规则引擎的计算口径（如储蓄率 = 月结余 / 月收入）遵循《AI 财富管家产品设计》第 6 章定义。
- 报告产物复用现有文档/Block 体系作为承载，读真相源、写报告，不反向写财务数据。
- 用户已登录，所有数据按用户隔离，身份与权限体系沿用项目现有机制。
- 沿用领域原则：领域模型是真相源，文档/Block 仅作报告层。
