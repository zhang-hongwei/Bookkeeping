# Feature Specification: 复式记账核心地基 (Phase 0)

**Feature Branch**: `001-double-entry-ledger`
**Created**: 2026-06-29
**Status**: Draft
**Input**: User description: "先完成第一阶段的规划"（指《AI 财富管家产品设计》`docs/product-design/ai-wealth-manager.md` 中的 Phase 0）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 手动记录收支与转账 (Priority: P1)

作为一个想要管钱的人，我希望能在几秒内记录一笔收入、支出或转账，并相信系统算出的每个账户余额永远是对的、账目永远是平的。

**Why this priority**: 这是整个产品的地基。没有「准确且永远平衡的账目」，后续的净资产、投资、AI 报告全都不可信。它本身已构成可独立交付的价值（一个能正确记账的最小账本）。

**Independent Test**: 创建几个账户，连续录入若干笔收入/支出/转账后，逐一核对每个账户余额与「初始余额 + 相关交易汇总」一致，且总账借贷平衡。即便只交付这一个故事，用户也得到了一个可用的准确账本。

**Acceptance Scenarios**:

1. **Given** 用户有一个「现金」账户余额 ¥1,000，**When** 记录一笔餐饮支出 ¥100（来源：现金），**Then** 现金余额变为 ¥900，且该笔支出如实反映为净支出 ¥100。
2. **Given** 用户有「现金」¥1,000 和「招行储蓄」¥5,000，**When** 记录一笔转账 ¥500（现金 → 招行储蓄），**Then** 现金变为 ¥500、招行储蓄变为 ¥5,500，且**用户净资产总额不变**（这笔转账不计入收入或支出）。
3. **Given** 用户记录一笔工资收入 ¥10,000（入账：招行储蓄），**Then** 招行储蓄余额 +¥10,000，且如实反映为净收入 ¥10,000。
4. **Given** 任意已记录的交易集合，**When** 查看任意账户余额，**Then** 余额恒等于该账户的初始余额与全部相关交易的汇总，不存在「对不上」的情况。

### User Story 2 - 管理自己的资金账户 (Priority: P2)

作为一个有多处资金存放位置的人，我希望能建立并管理自己的账户（现金、银行卡、信用卡），随时看到每个位置的真实余额。

**Why this priority**: 账户是「钱存放的位置」，是交易与净资产的基础。它让记账从「记流水」升级为「按资金位置管理」，是 P1 记账能落地的前提。

**Independent Test**: 创建现金 / 储蓄 / 信用三类账户并设置初始余额，记录交易后，每类账户余额都正确变化；归档一个账户后历史不丢失、也不再参与新交易。

**Acceptance Scenarios**:

1. **Given** 用户首次使用，**When** 创建「微信零钱」(现金类)、「招商银行」(储蓄类)、「招行信用卡」(信用类) 三个账户并填入当前余额，**Then** 三账户初始余额正确显示。
2. **Given** 用户有一个不再使用的账户，**When** 将其归档，**Then** 该账户的历史交易保留可见、余额仍正确，但不再作为新交易的默认可选账户。
3. **Given** 信用类账户记录了一笔消费 ¥200，**Then** 其余额按信用账户的记账方向正确变化（体现为欠款/占用）。

### User Story 3 - 批量导入账单，告别逐笔录入 (Priority: P3)

作为一个已有大量历史流水的人，我希望能把支付宝/微信导出的账单文件一次性导入，系统自动解析、归类，并让我预览确认后才落库。

**Why this priority**: 录入摩擦是这类产品的头号死亡线。批量导入是降低摩擦、让用户愿意持续使用的关键，是 P1/P2 之后最高杠杆的能力。

**Independent Test**: 上传一份真实的支付宝/微信账单文件，系统解析为交易列表并预览，用户确认后所有交易正确落库、账目仍平衡；同一文件重复上传不会产生重复交易。

**Acceptance Scenarios**:

1. **Given** 用户从支付宝/微信导出了一份账单文件，**When** 上传该文件，**Then** 系统解析出候选交易列表（金额、时间、对方/备注、建议分类、目标账户），进入可预览状态。
2. **Given** 解析后的候选交易列表，**When** 用户预览并确认，**Then** 这些交易落库，相关账户余额正确更新，账目保持平衡。
3. **Given** 用户已经导入过某份账单，**When** 再次上传同一份文件，**Then** 系统识别为重复并跳过/提示，不产生重复交易。

### User Story 4 - 一句话/对话记账 (Priority: P4)

作为一个怕麻烦的人，我希望能用一句话（如「午饭 35」「打车 18 去公司」）或在与助手的对话中完成记账，系统帮我解析成一笔交易，并让我确认。

**Why this priority**: 进一步降低录入摩擦，是差异化体验。优先级低于批量导入（覆盖面更广），但能显著提升日常随手记的意愿。

**Independent Test**: 输入「午饭 35」，系统生成一笔金额 ¥35、分类餐饮、默认账户与当前时间的候选交易，用户确认后落库且账目平衡。

**Acceptance Scenarios**:

1. **Given** 用户在记账入口输入「午饭 35」，**When** 提交，**Then** 系统生成候选交易（支出 ¥35、分类=餐饮、默认账户、时间=当前），展示给用户确认。
2. **Given** 自然语言包含账户或时间线索（如「昨天用招行卡买书 120」），**When** 解析，**Then** 候选交易正确反映账户与时间。
3. **Given** 输入无法被可靠解析（如「那个东西花了挺多」），**When** 提交，**Then** 系统给出友好提示并允许用户手动补全，而不是错误落库。

---

### Edge Cases

- **转账/支出超过当前余额**：默认允许（如信用卡天然为负/欠款），系统不硬性拦截，仅在余额为负时给出轻提示。是否启用「透支拦截」留待后续阶段。
- **重复导入同一账单文件**：必须被识别并跳过，绝不产生重复交易（见 US3）。
- **编辑或删除一笔历史交易**：所有相关账户余额必须同步重新计算并保持平衡，不得出现历史残留导致的错账。
- **同一笔交易涉及金额为 0 或负数**：金额必须为正；负数/零应被校验拒绝或要求修正。
- **交易时间在过去或未来**：允许（补记/预定），但默认为当前时间；需在明细中如实显示其发生时间。
- **跨币种**：Phase 0 单币种（CNY），跨币种/汇率不在本阶段范围。
- **账户被归档后仍被引用为历史交易的目标账户**：历史数据保留可读，归档仅影响「新交易的可选性」。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户创建资金账户，必填类型（现金 / 储蓄 / 信用）、名称、初始余额，默认币种为 CNY。
- **FR-002**: 系统 MUST 允许用户归档与恢复账户；归档后历史交易与余额保留可读，但不再作为新交易的默认选项。
- **FR-003**: 系统 MUST 允许用户记录交易，支持三种类型：收入 / 支出 / 转账；必填金额（须为正）、发生时间、相关账户；可选分类、备注、来源标记。
- **FR-004**: 系统 MUST 确保「转账」仅移动资金、不计入收入或支出（不扭曲收支统计与净资产）。
- **FR-005**: 系统 MUST 在任何记账/编辑/删除操作后保持账目平衡（复式记账不变式）：账户余额恒等于其初始余额与全部相关交易的汇总，账目不平衡发生率须为 0。
- **FR-006**: 系统 MUST 提供账户余额与交易明细的查看，支持按时间、账户、分类筛选。
- **FR-007**: 系统 MUST 允许编辑或删除已记录交易，并在操作后同步重算所有相关账户余额、保持账目平衡。
- **FR-008**: 系统 MUST 支持从账单文件（CSV 等）批量导入交易：自动解析金额/时间/对方/分类、建议目标账户、提供预览、经用户确认后落库。
- **FR-009**: 系统 MUST 对导入交易进行去重，避免同一账单重复导入产生重复记录。
- **FR-010**: 系统 MUST 支持自然语言记账：将一句话解析为候选交易（金额/分类/账户/时间），供用户确认后落库；解析失败时给出提示并允许手动补全。
- **FR-011**: 系统 MUST 提供分类管理，含默认收支分类、用户自定义分类、以及基于关键字/规则的自动归类。
- **FR-012**: 系统 MUST 对每条交易记录其来源（手动 / 批量导入 / 自然语言）与置信度，便于后续审计与低置信数据标注。
- **FR-013**: 系统 MUST 保证数据按用户隔离，用户只能查看与操作属于自己的账户、交易与分类。

### Key Entities *(include if feature involves data)*

- **账户 (Account)**：资金存放的位置（现金 / 储蓄 / 信用）。每个账户有类型、名称、初始余额、当前余额（由交易汇总得出，而非独立维护）。
- **交易 (Transaction)**：一笔收支或转账业务事件。含类型（收入/支出/转账）、金额、发生时间、分类、备注、来源与置信度。
- **分录 (Entry)**：一笔交易在账户侧的记账腿；一笔交易由若干条相互平衡的分录组成——这是「账目永远平衡」的依据（核心不变式）。
- **分类 (Category)**：收支归类，支持父子层级与自动归类规则。
- **账单导入批次 (Bill Import)**：一次批量导入的会话，含来源文件、解析出的候选交易、解析/确认状态，便于预览、确认与去重。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：任意收入/支出/转账/编辑/删除操作后，所有账户余额与净影响始终自洽，账目不平衡发生率 = 0。
- **SC-002**：任何转账操作不改变用户净资产总额（仅改变资金所在位置）。
- **SC-003**：用户完成一笔手动记账（含选账户与分类）平均耗时 ≤ 15 秒。
- **SC-004**：标准格式的支付宝/微信账单文件，导入解析准确率 ≥ 95%，且导入后账目仍平衡。
- **SC-005**：自然语言记账（如「午饭 35」）首次解析即可生成可用候选交易的成功率 ≥ 90%。
- **SC-006**：同一账单文件重复导入被识别并跳过，重复交易产生率 = 0。
- **SC-007**：编辑或删除任意一笔历史交易后，所有相关账户余额在一次操作内同步正确。

## Assumptions

- 单币种 CNY 起步；多币种、汇率换算不在本阶段范围。
- 信用类账户在 Phase 0 仅作为「信用账户」记录余额与消费（按信用方向记账）；账单周期、还款、分期、免息期等细节属于后续阶段。
- 「净资产仪表盘」「资产/负债明细」「投资与实物资产」属于后续阶段（Phase 1+），Phase 0 不交付这些界面；Phase 0 只保证账目数据正确，为后续净资产计算打好地基。
- 自然语言解析与账单解析依赖现有 AI 对话能力（在线）。
- 余额不足时不做硬性拦截，允许负余额（如信用卡欠款），仅给出轻提示；「透支拦截」属后续可选能力。
- 用户已登录，所有数据按用户隔离；身份与权限体系沿用项目现有机制。
- 沿用《AI 财富管家产品设计》的领域原则：领域模型是真相源，文档/Block 仅作为后续报告层；本阶段不涉及报告层。
