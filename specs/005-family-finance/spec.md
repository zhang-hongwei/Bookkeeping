## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把家人加进来，看到家庭整体的财富 (Priority: P1)

作为一个管家庭账的人，我希望能把伴侣/家人加入同一个家庭，看到全家合并的净资产与收支，而不只是我自己的。

**Why this priority**: 中国家庭财务是「家庭为单位」而非个人。合并视图是产品从「个人记账」走向「家庭 CFO」的关键一步，也是复用已有个人模型（仅加成员维度）的高杠杆扩展。

**Independent Test**: 两个成员各自录入自己的账户与交易，切换到家庭视图后，家庭净资产 = 成员 A 净资产 + 成员 B 净资产，家庭收支合并呈现。

**Acceptance Scenarios**:

1. **Given** 用户已建立个人财务，**When** 创建家庭并邀请伴侣加入，**Then** 双方成为同一家庭的成员，各自保留独立个人视图。
2. **Given** 家庭有两个成员各自有账户与交易，**When** 切换到「家庭合并视图」，**Then** 家庭净资产 = 各成员净资产之和，家庭收支为各成员合并，且可按成员拆分查看。
3. **Given** 家庭合并视图，**When** 查看净资产曲线，**Then** 呈现家庭合并净资产随时间的变化，与各成员曲线之和要求一致。

---

### User Story 2 - 知道这笔钱是谁花、谁赚的 (Priority: P2)

作为一个想了解家庭消费结构的人，我希望每笔交易能标记是哪个成员花的/赚的，这样能看到每个人的支出画像与对家庭的贡献。

**Why this priority**: 成员归属是「家庭财务分析」的基础维度。没有它，合并视图只是一堆无主数字。标记 memberId 让家庭账目可按人拆解，是家庭顾问的前提。

**Independent Test**: 多笔交易分别标记不同成员，系统按成员汇总各自的收支与净资产贡献，呈现成员支出画像。

**Acceptance Scenarios**:

1. **Given** 用户记录一笔家庭支出，**When** 标记归属成员（如「伴侣」），**Then** 该笔计入伴侣的支出画像与家庭合并支出。
2. **Given** 家庭多成员的交易均带成员归属，**When** 查看成员画像，**Then** 各成员的收支、结余、主要消费分类分别呈现。
3. **Given** 一笔交易属于共同消费（如全家旅游），**When** 标记，**Then** 可标记为共同/家庭，不单算到某一人。

---

### User Story 3 - 我的私房钱只有我自己能看 (Priority: P3)

作为一个有个人隐私的人，我希望可以选择某些账户/交易不与家庭共享，保留纯个人视图，不被家人看到。

**Why this priority**: 家庭合并涉及隐私边界。必须让用户可控地决定「共享什么、保留什么」，否则信任门槛过高、用户不敢把全部家底交出来。这是家庭功能能否被接受的前提。

**Independent Test**: 用户将某个账户标记为「仅个人」，该账户在家庭合并视图中不可见、不并入家庭净资产，仅本人可见。

**Acceptance Scenarios**:

1. **Given** 用户有一个不想共享的账户，**When** 标记为「仅个人/不共享」，**Then** 该账户在家庭合并视图中不可见，不并入家庭净资产。
2. **Given** 家庭成员权限，**When** 某成员查看家庭视图，**Then** 仅能看到被共享的数据，看不到他人标记为「仅个人」的部分。
3. **Given** 用户想退出家庭共享，**When** 操作，**Then** 其个人数据完整保留、不再并入该家庭，且其历史共享数据按既定规则处理。

---

### Edge Cases

- **共同账户/共同消费**：家庭共用的账户或多人均受益的支出（如水电/旅游），需支持「共同」归属，而非强制单算到一人。
- **成员退出家庭**：成员离开后其个人数据须完整保留且不再并入家庭合并；历史家庭报表的处理需明确（保留快照 vs 重算）。
- **家庭 vs 个人视图切换**：切换须瞬时、无数据串扰；默认视图（个人/家庭）应由用户可配。
- **重复/交叉账户**：避免家庭合并时同一笔资金被双计入（如夫妻共有账户被双方各登记一次）。
- **多家庭/复杂结构**：本阶段聚焦单一家庭；一人多家庭（如同时管自己家与父母家）不在本阶段核心范围。
- **权限边界越权**：任何情况下成员不得越过共享范围查看他人隐私数据，越权访问须被拒绝。
- **成员未注册/未加入**：为尚未使用系统的家人预占成员槽位（仅记账归属，无登录账号）的支持可作为可选增强。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持「家庭」实体与成员管理：创建家庭、邀请/加入成员、成员带角色（如本人/伴侣/子女）与共享范围。
- **FR-002**: 系统 MUST 支持交易标记成员归属（memberId：谁花/谁赚），并支持「共同/家庭」归属用于共同消费。
- **FR-003**: 系统 MUST 提供家庭合并视图：家庭净资产 = 各成员净资产之和，家庭收支为各成员合并，且可按成员拆分查看。
- **FR-004**: 系统 MUST 提供成员支出画像：按成员汇总各自收支、结余与主要消费分类。
- **FR-005**: 系统 MUST 支持共享范围控制：账户/交易可标记「仅个人/不共享」，被标记项在家庭合并视图中不可见、不并入家庭净资产。
- **FR-006**: 系统 MUST 保证权限边界：成员只能看到被共享的数据，越权访问他人「仅个人」数据须被拒绝；家庭净资产计算须排除不共享项、不重复计入。
- **FR-007**: 系统 MUST 支持成员退出家庭：其个人数据完整保留、不再并入该家庭；退出对历史家庭报表的影响须明确（保留快照）。
- **FR-008**: 系统 MUST 允许用户配置默认视图（个人/家庭），切换瞬时且无数据串扰。
- **FR-009**: 系统 MUST 保证家庭合并净资产与逐成员汇总一致，重复/交叉计入发生率为 0。

### Key Entities *(include if feature involves data)*

- **家庭 (Family)**：多成员的财务聚合单位，含成员列表与共享配置。
- **家庭成员 (Family Member)**：家庭中的成员，关联用户账号（或预占槽位）、带角色与共享范围。
- **成员归属 (Member Attribution)**：交易上的归属维度（哪个成员花/赚，或「共同」），用于按人拆解与合并。
- **共享范围 (Share Scope)**：账户/交易是否纳入家庭合并的标记（共享 / 仅个人），是隐私边界的依据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：家庭合并视图净资产 = 各成员净资产之和，与逐成员手动汇总一致，不一致/重复计入发生率 = 0。
- **SC-002**：标记「仅个人」的账户/交易在家庭合并视图中 100% 不可见、不并入家庭净资产。
- **SC-003**：成员越权访问他人「仅个人」数据被 100% 拒绝。
- **SC-004**：成员退出家庭后，其个人数据完整保留、不再并入家庭合并，历史家庭报表以快照保留。
- **SC-005**：个人/家庭视图切换瞬时完成，无数据串扰。

## Assumptions

- 本阶段依赖 Phase 0–3 已建立的完整个人财务模型（账户、交易、分录、资产/负债、投资、净资产快照）。
- 家庭成员需为已注册用户才能登录查看；为未注册家人预占槽位（仅记账归属）为可选增强，非本阶段核心。
- 默认隐私优先：账户/交易默认是否共享由用户显式选择，倾向「保守共享」（对应设计第 9 章 local-first/信任优先、D4）。
- 本阶段聚焦单一家庭结构；一人同时管多个家庭不在本阶段核心范围。
- 家庭报表结论仍走规则引擎（沿用 Phase 1+ 规则引擎/LLM 表达层）。
- 用户已登录，所有数据按用户/家庭隔离，身份与权限沿用并扩展现有机制。
- 沿用领域原则：成员归属/共享范围走领域模型。
