**Created**: 2026-06-29
**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 给每类开销设个预算，超支立刻知道 (Priority: P1)

作为一个想控制开销的人，我希望能给「餐饮/购物/交通」等分类设月度预算，随时看到已花多少、剩多少，并在快要超支或已超支时被提醒。

**Why this priority**: 预算是「主动控制支出」最直接的工具，也是规则引擎（超支检测）高频产出的场景。实时已用/剩余 + 超支预警，把记账从「事后看」升级为「事中管」，是留存与价值感的高频抓手。

**Independent Test**: 给「餐饮」设月预算 ¥2,000，记录若干餐饮支出后，系统实时显示已用/剩余；当支出达到 ¥2,000 时触发超支提示。

**Acceptance Scenarios**:

1. **Given** 用户想控制餐饮开销，**When** 给「餐饮」分类设月度预算 ¥2,000，**Then** 预算生效，显示本月已用/剩余。
2. **Given** 本月已记餐饮支出 ¥1,500，**When** 又记一笔 ¥600，**Then** 已用变为 ¥2,100、超出预算 ¥100，并实时给出超支提示。
3. **Given** 接近预算阈值（如达 80%），**When** 触发，**Then** 系统给出「即将超支」预警，帮助提前控制。
4. **Given** 跨月，**When** 进入新月，**Then** 预算按周期自动重置，已用清零、历史预算周期可回溯。

---

### User Story 2 - 设定财务目标，看到离目标还有多远 (Priority: P2)

作为一个有存钱目标的人，我希望能设定「买房首付/旅游/应急金/退休」等目标，看到当前进度、完成率，以及按当前结余节奏预计何时达成。

**Why this priority**: 目标把储蓄从「漫无目的」变成「有奔头」，预计达成时间是「未来会怎样」这一产品承诺的雏形。它复用净资产/结余数据，杠杆高。

**Independent Test**: 设定一个目标（金额 + 截止），关联已有资金后显示进度与完成率；按近 3 个月平均结余计算预计达成时间。

**Acceptance Scenarios**:

1. **Given** 用户想存旅游基金 ¥30,000，**When** 设定目标并关联已有储蓄 ¥10,000，**Then** 显示进度 33%、完成率。
2. **Given** 上述目标，**When** 用户近期月均结余 ¥5,000，**Then** 系统按结余节奏估算预计达成时间（约 4 个月）。
3. **Given** 用户结余率变化（如降薪导致月结余减少），**When** 数据更新，**Then** 预计达成时间随之刷新。
4. **Given** 目标达成，**When** 进度到 100%，**Then** 系统标记目标完成并提示。

### User Story 3 - 预算超支与目标进度由规则驱动，可信赖 (Priority: P3)

作为一个依赖这些提醒做决定的人，我希望超支预警和目标进度都是基于真实账目算出来的、确定性的，而不是 AI 猜的。

**Why this priority**: 沿用设计 P5「规则引擎负责准确，LLM 负责表达」。预算/目标的数值结论必须来自规则引擎，LLM 只做个性化建议，保证可信赖、零幻觉。

**Independent Test**: 触发一次超支预警，其数值（已用/超支额）100% 来自账目与规则；目标预计达成时间基于历史结余的明确算法，可复现。

**Acceptance Scenarios**:

1. **Given** 触发超支预警，**When** 查看其数值，**Then** 已用/剩余/超支额均来自账目汇总与规则，可逐项追溯。
2. **Given** 目标预计达成时间，**When** 查看其依据，**Then** 基于历史结余的明确算法（如近 N 月均值），可复现、可解释。
3. **Given** LLM 给出的「如何改善」建议，**When** 查看，**Then** 建议基于规则结论，不自行编造金额数字。

---

### Edge Cases

- **预算周期**：默认月度，应支持按周/年等周期；周期切换时已用须按周期正确归集。
- **跨分类/多分类预算**：一笔支出可能影响多个预算（父子分类），须避免重复计入或漏计。
- **目标资金来源**：目标可关联具体账户/资金，需明确「目标进度」是基于关联资金还是总净资产，避免歧义。
- **负结余/无法达成**：当近期结余为负或为 0 时，预计达成时间应显示「按当前节奏无法达成/需调整」，而非错误数值或虚假乐观。
- **目标无截止日**：允许设无截止日的开放式目标（如应急金），此时仅显示进度、不估算达成时间。
- **预算调整**：用户中途修改预算额度，已用/剩余须按新额度正确反映，历史周期不变。
- **多币种**：仍为单币种 CNY。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持按分类设定预算，含周期（默认月度，支持周/年）、额度；并实时计算已用、剩余、状态（正常/即将超支/已超支）。
- **FR-002**: 系统 MUST 在支出计入受预算分类时实时更新已用/剩余，并在达到阈值（如 80%）或超支时给出预警。
- **FR-003**: 系统 MUST 在预算周期跨月/切换时自动重置已用，并保留历史预算周期供回溯。
- **FR-004**: 系统 MUST 正确处理父子分类与多预算重叠，避免一笔支出被重复计入或漏计。
- **FR-005**: 系统 MUST 支持财务目标：设定名称、目标金额、（可选）截止日，关联资金后显示当前金额、进度率。
- **FR-006**: 系统 MUST 基于历史结余（明确算法，如近 N 月均值）估算目标预计达成时间；结余为负/为 0 时明确提示「按当前节奏无法达成」。
- **FR-007**: 系统 MUST 在用户结余率/关联资金变化后刷新目标进度与预计达成时间。
- **FR-008**: 系统 MUST 保证预算与目标的所有数值结论（已用/剩余/超支额/进度/预计达成）来自规则引擎与账目数据，可逐项追溯、可复现；LLM 仅负责个性化建议。
- **FR-009**: 系统 MUST 保证所有数据按用户（及家庭成员，若启用 Phase 4）隔离。

### Key Entities *(include if feature involves data)*

- **预算 (Budget)**：某分类在某周期（如月度）的支出限额，含已用、剩余、状态（均为基于账目的派生值）。
- **目标 (Goal)**：财务储蓄目标，含名称、目标金额、当前金额（派生）、截止日、进度率（派生）、预计达成时间（派生）。
- **规则结论 (Rule Finding)**（复用 Phase 1）：预算超支/目标进度的确定性结论，作为提醒与 LLM 建议的事实输入。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：分类预算的已用/剩余在每笔相关支出后实时正确更新，与账目汇总一致，不一致发生率 = 0。
- **SC-002**：支出达到阈值/超支时实时触发预警（事中而非仅事后）。
- **SC-003**：目标进度与预计达成时间基于历史结余的明确算法可复现；结余为负/0 时正确提示无法达成，不产生虚假乐观数值。
- **SC-004**：预算与目标的所有数值结论 100% 来自规则引擎/账目，可逐项追溯；LLM 不编造金额数字。
- **SC-005**：预算跨月自动重置，历史周期可回溯，无串扰。

## Assumptions

- 本阶段依赖 Phase 0（分类/交易）与 Phase 1（规则引擎/净资产结余）。
- 预算默认月度周期、单币种 CNY。
- 预计达成时间算法采用明确口径（如近 3–6 月平均结余），具体窗口在实现阶段确定但须可解释、可复现。
- 预算/目标提醒走规则引擎；个性化建议走 LLM 表达层（沿用 Phase 1 双层架构）。
- 若 Phase 4（家庭）已启用，预算/目标可按成员或家庭维度，但本 spec 核心范围以个人为主。
- 用户已登录，所有数据按用户隔离，身份与权限沿用项目现有机制。
- 沿用领域原则：预算/目标走领域模型，结论走规则引擎。
